# Super Admin Portal

The platform-operator tooling for PropertyVault's own team — not a client-facing feature, not visible or reachable by any client organization role. This document is the implementation-grounded design referenced by `PERMISSIONS.md` §6 ("Full design in `SUPER_ADMIN.md`"). It reproduces the master prompt's Super Admin requirements and cross-references each item against the schema/API that actually exists today (`DATABASE.md`, `API_SPEC.md`), flagging what still needs new infrastructure.

## 0. Where it lives

Per `ARCHITECTURE.md` ("Why one web app, not two"): the Super Admin portal is **not** a role tier layered onto client org roles. It is a separate route group in the same Next.js app — `app/(super-admin)/**` in `apps/web` (the renamed/refactored `apps/admin`) — sitting alongside the client route group `app/(dashboard)/**`. Access is gated by an independent auth check against `platform_admin_users` membership, never by an org role claim. A client `principal` and a platform `super_admin` are unrelated types; conflating them was the exact anti-pattern the master prompt warns against.

**Reused from `apps/admin` as-is** (`EXISTING_CODEBASE_AUDIT.md` §4–§5):

- The Next.js App Router shell, Supabase Auth + `middleware.ts` gating pattern.
- `getAdminSession()` / `requireRole(minRole)` in `lib/auth.ts` — resolves the caller against `platform_admin_users` (formerly `admin_users`) via the service-role client, re-checked in every route handler (middleware alone is documented as bypassable).
- `isRoleAtLeast()` / `ROLE_RANK` in `lib/roleRank.ts` — pure rank comparison, directly reusable for the four platform roles below (already defines exactly `read_only_admin < support_admin < operations_admin < super_admin`).
- UI primitives: `AdminDataTable`, `AdminMetricCard`, `HealthStatusIndicator`, `MiniBarChart`, `MiniLineChart` — generic, no single-owner-domain coupling in their props.

**Not reused — needs rebuilding**: everything the existing `apps/admin` pages actually _render_. `customers/page.tsx` and `CustomersTable` model one individual owner-operator per row; the Super Admin directory needs to model a client **organization** (with staff, properties, tenants underneath it), which is a different data shape, not a relabeling. `subscriptions/page.tsx` needs to move from a single hardcoded plan to the `plans`/`organization_subscriptions` model (§5 below). `system/page.tsx`'s "not yet connected" pattern for unimplemented integrations is worth keeping as a UX convention.

## 1. Platform roles

From `PERMISSIONS.md` §1, backed by `platform_admin_users.role` (`DATABASE.md` §1):

| Role               | Scope                                                                                                    |
| ------------------ | -------------------------------------------------------------------------------------------------------- |
| `super_admin`      | Full portal: all client orgs, billing/plan configuration, support-mode access, platform-staff management |
| `support_admin`    | Client org read access + support-mode entry (audited); cannot change billing/plans                       |
| `operations_admin` | Platform health/usage monitoring; cannot enter support mode or view client business data                 |
| `read_only_admin`  | Read-only across the whole portal; no writes anywhere                                                    |

Enforced by `requireRole(minRole)` / `is_platform_admin(min_role)` (`security definer`), checked in every Super Admin route handler — never via a client-supplied role claim. No client RLS policy exists on `platform_admin_users`; it is service-role/`is_platform_admin()`-only, matching the `[RETAINED PATTERN]` marked in `DATABASE.md` §1. (Both `platform_admin_users` and `is_platform_admin()` are target names — the live schema still has `admin_users`/`is_admin()` until the Milestone 13 rename, `DATABASE.md` §1.)

The role-to-action mapping in the sections below (dashboard = `read_only_admin`+, billing writes = `super_admin` only, etc.) follows the same least-privilege shape as the PropVault-era `ADMIN_DASHBOARD.md`, adjusted for the org-level (not individual-customer-level) data model.

### 2.2 Partially supported

| Metric          | Note                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       |
| --------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| System errors   | No dedicated error-tracking table in `DATABASE.md`. `audit_events` (§1, DATABASE.md §10) captures user/system/api actions with before/after state, but is an audit trail, not an error log. If a dedicated error-monitoring service (e.g. `packages/utils/errorMonitoring`, referenced in `EXISTING_CODEBASE_AUDIT.md` §6) is wired up, this metric comes from there, not Postgres.                                                                                                                        |
| Platform health | The old `apps/admin` `system/page.tsx` pattern (live counts + explicit "not yet connected" states for unwired integrations) is the right UX model, but "health" needs a definition: uptime/error-rate from infra monitoring (external to this schema) plus DB-derivable signals (failed payment rate, `ocr_jobs` failure rate — `DATABASE.md` §6 — stuck `support_access_sessions`, etc.). Recommend composing this from multiple existing signals rather than inventing a single `platform_health` table. |

### 2.3 Usage tracking — resolved by architecture review, 2026-07-30

**Closed** (was previously a gap flagged here): `DATABASE.md` §7 now defines `usage_events` (fine-grained, written by each subsystem as it consumes a resource) and `usage_snapshots` (periodic per-org/period/type rollup, what this dashboard and the client directory in §3 actually read). Platform storage/email/WhatsApp/OCR/AI usage per org are all `usage_type` values in the same enum — one mechanism, not five bespoke trackers. The dashboard/directory metrics below read `usage_snapshots`, not raw `usage_events`.

**Historical credit-issuance / discount-application events**: `organization_subscriptions.promotional_credit`/`discount_pct` capture current state, not an auditable "credit issued on date X, by admin Y, reason Z" log. `support_access_sessions.actions_taken` (§4 below) covers actions taken _during a support session_, but a credit/discount applied outside support mode (the normal case — see §5) has no dedicated event log today. Recommend either logging these through `audit_events` (`entity_type = 'organization_subscriptions'`, `action = 'credit_issued'`, `before`/`after` capturing the amount) — which the schema already supports — or a purpose-built table if reporting needs grow beyond what `audit_events` queries comfortably. **Not a hard schema gap** (audit_events covers it) but worth calling out explicitly since it wasn't named as such anywhere.

## 5. Billing configuration

Backed entirely by tables that already exist — no schema gap here, only implementation work:

- **Plans are configurable, not hardcoded** (`plans` table, `DATABASE.md` §1): `code`, `name`, `billing_cycle`, `base_price`, `currency`, `feature_limits jsonb`, `is_active`, `version int`. A price change creates a new `version`; existing subscriptions keep the version they signed up under unless explicitly migrated — this is the plan-versioning requirement, already modeled.
- **Client-specific pricing**: `organization_subscriptions.price_override` — nullable, overrides the plan's `base_price` for that org.
- **Discounts**: `organization_subscriptions.discount_pct`.
- **Promotional credits**: `organization_subscriptions.promotional_credit` (defaults to 0).
- **Billing cycles**: `organization_subscriptions.billing_cycle`, independent of the plan's default cycle (an org can be on a different cycle than the plan's nominal one — worth confirming this is the intended semantics vs. `billing_cycle` always mirroring the plan).
- **Tax**: `organizations.vat_no`, `sars_tax_no` — tax _treatment_ (VAT-registered vs. not) is derived from presence of these fields; no separate tax-rate/tax-rule table exists, which is fine if PropertyVault applies a single jurisdiction's rules (South Africa, per `cipc_reg_no`/`sars_tax_no`/`ffc_number` fields) rather than needing multi-jurisdiction tax configuration.
- **Overdue / suspension / cancellation rules**: `organizations.status` and `organization_subscriptions.status` both carry the same enum (`trial|active|overdue|suspended|cancelled`). The _rules_ that transition between these states (e.g. "N days unpaid → overdue → suspended") are not schema — they're business logic that belongs in a scheduled job or the payment-webhook handler, consulting `subscription_payments.status`/`next_payment_date`. **Flagged**: no such job/handler is described in `API_SPEC.md` yet; this needs a defined policy (grace period lengths, etc.) before implementation, not a schema change.
- **Subscription history**: `organization_subscriptions` is explicitly append-only per period (`DATABASE.md` §1 — "this table is append-only per period, not updated in place"), so plan changes/upgrades/downgrades are already historical by design; `organizations.status` denormalizes current status for fast dashboard queries.

## 6. Support mode

Backed by `support_access_sessions` (`DATABASE.md` §1) and `PERMISSIONS.md` §6. Design, made concrete against the actual table columns:

- **Requires explicit reason**: `support_access_sessions.reason text not null` — enforced at the DB level (`not null`), not just a UI-required field. `POST /api/v1/admin/support-sessions` must 400 if `reason` is missing/empty.
- **Immutable audit entry**: `started_at`/`reason` are insert-only per `DATABASE.md` §1 ("Insert-only for `started_at`/`reason`"). Only `ended_at` is ever updated, and only by the session closing itself or an automatic timeout — never by editing the record's history.
- **Records admin identity + org + start/end time**: `platform_admin_id FK`, `org_id FK`, `started_at`, `ended_at nullable` — all present in the table as designed.
- **Visible banner during the session**: UI requirement on the Super Admin app — while a `support_access_sessions` row has `ended_at is null` for the current admin, every page renders a persistent, non-dismissible banner naming the target org and the session's `started_at`. This is a frontend obligation with no schema counterpart; note it here so it isn't dropped during implementation.
- **Never silent/invisible unrestricted impersonation**: enforced structurally — there is no "become this user" credential swap; support mode is a scoped session tracked in its own table, not an auth-token substitution. `PERMISSIONS.md` §6 confirms: "never a blanket impersonation that silently grants `principal`-equivalent access."
- **Restricts sensitive actions — concrete design**:
  1. **Read-only by default.** On entering support mode, the platform admin's requests against the target org are scoped as if they held the `viewer` org role (`DATABASE.md` §12 RLS pattern, `PERMISSIONS.md` §2) — they can see what a `viewer` staff member of that org could see, nothing more, without any further action.
  2. **Explicit escalation per write.** Any write action (e.g. correcting a lease record to diagnose a bug) requires a separate, explicit escalation call within the same session — not a mode-wide unlock. Each escalated write is logged as its own entry appended to `support_access_sessions.actions_taken jsonb[]` (`DATABASE.md` §1: "append-only log of what was done during the session"), recording at minimum: `{ action, entity_type, entity_id, timestamp }`, mirroring the `audit_events` shape (§10) so the two logs stay consistent and cross-referenceable.
  3. **Never** — regardless of escalation — access to the target org's `encrypted_secrets`-backed fields (bank account numbers, ID numbers — `DATABASE.md` §11) or trigger financial postings (`journal_entries`/`journal_lines` are insert-only with no `update`/`delete` policy for _any_ role per §12, and support mode does not carry `accountant`/`principal`-equivalent posting rights even under escalation — posting stays a client-org-role-only action).
  4. **Session end**: `POST /api/v1/admin/support-sessions/:id/end` sets `ended_at`; the banner disappears; the admin's next request against that org is denied (no residual access) — enforced the same way normal org-membership RLS denies a non-member, since support mode never grants an `organization_members` row, only a parallel, time-boxed grant checked by the API layer alongside RLS.

## 7. Open gaps summary (for follow-up, not resolved here)

1. ~~Usage metering~~ — **resolved, architecture review 2026-07-30**: `usage_events`/`usage_snapshots` now in `DATABASE.md` §7 (see §2.3 above).
2. **Churn rate computation** — derivable from existing append-only `organization_subscriptions` history but needs a helper view/materialization, not new tables.
3. **Credit/discount issuance history** — coverable via `audit_events` (no schema gap), but not currently named as a required audit pattern anywhere; worth stating explicitly when the credits/discount endpoints are built.
4. ~~"Archive" as a client status~~ — **resolved, architecture review 2026-07-30**: `organizations.status` gained an `archived` value (`DATABASE.md` §1); `POST /api/v1/admin/organizations/:orgId/archive` is the corresponding action.
5. **Overdue/suspension/cancellation transition rules** (grace periods, automatic triggers) — business logic, not schema; no scheduled job or webhook handler for this is described yet in `API_SPEC.md`.
6. **Account-recovery workflow** — needs its own identity-verification design (analogous to support mode's reason+audit requirement) before implementation; flagged, not designed here.
7. **System errors / platform health** metrics — no dedicated error-tracking or health table; recommend composing from `audit_events`, `ocr_jobs` failure rates, and external infra monitoring rather than a new all-purpose table.
