# Mobile Architecture Decision

## 1. Current state (verified)

A repo-wide search for `.xcodeproj`, `.xcworkspace`, `build.gradle`, and `AndroidManifest.xml` (excluding `node_modules`) returned **zero results**. `apps/mobile` is a pure Expo-managed-workflow React Native app (`expo@~56.0.16`, `react-native@0.85.3`, Expo Router). There is no Xcode project, no Android Studio project, and no native build tooling anywhere in this repository today.

## 2. iOS classification

Per the master prompt §17, classify as: **Missing.** There is no Swift code, no SwiftUI, no UIKit, no Xcode project. The existing Expo app is JavaScript/TypeScript rendered through React Native's iOS runtime — this is explicitly the pattern the master prompt disallows as a basis for the required native app (§8: "must not be implemented as only... a cross-platform substitute unless explicitly approved later"). Nothing here is reusable as _code_.

## 3. Android classification

Per the master prompt §17, classify as: **Missing**, same reasoning. No Kotlin, no Jetpack Compose, no XML Views, no Gradle project.

## 4. What the existing mobile app IS useful for

Not code — **reference**. `apps/mobile/src/design/components/` (design tokens, card/badge/empty-state/form patterns) and `apps/mobile/app/**` (the screen list and field-level detail of what each screen needs to show) are a faithful, already-validated translation of the PropView reference screenshots into a concrete component/field inventory. Rebuilding natively means re-implementing these _screens and flows_, not this _codebase_ — the existing app is a working spec, not a starting point to fork.

## 5. Decision: one native codebase per platform, role-aware navigation, not separate apps

**iOS**: Swift + SwiftUI, built and managed in Xcode. UIKit only where a specific native capability (documented case-by-case) has no practical SwiftUI path.

**Android**: Kotlin + Jetpack Compose, built via Android Studio/Gradle. XML Views only where a specific retained/justified case requires it (documented case-by-case); none currently exist since there's no prior Android code at all.

**Within each platform, one app, not two**: a single iOS app and a single Android app, each with role-aware navigation that switches between a Landlord/Owner experience and a Tenant experience based on the account's enabled portals — mirroring the portal-switcher pattern directly evidenced in the PropView reference (IMG_7969, 7983, 8073: one login, "Switch Portal" control, both a Landlord and Tenant identity available simultaneously on one account).

### Why one app per platform, not separate Owner and Tenant apps

- **Screenshot evidence directly supports it.** The reference product's own account model has one login holding both portal identities, switchable in-session — not two separate credentialed apps. A person who owns property they also happen to rent (or a property manager who's also a tenant somewhere) needs to switch, not re-authenticate into a different app.
- **App Store / Play Store management.** Two apps per platform (four listings total) roughly doubles store-review overhead, versioning coordination, and deep-link/universal-link configuration, for a split that the product's own data model (one account, multiple portal memberships) doesn't require.
- **Shared functionality is substantial.** Auth, biometric unlock, push notification handling, document viewing, maintenance-ticket submission UI, and settings are needed by both roles with only minor field differences — a single app with role-gated navigation shares this cleanly; two apps would duplicate it or force a shared-package split that adds build complexity without a corresponding security or UX benefit.
- **Security is not weakened by combining them.** Role-scoping happens the same way either way — server-side, via the org-membership/role model from `RETAIN_REFACTOR_REBUILD_MATRIX.md`. A tenant using the combined app cannot see landlord data for the same reason a tenant using a hypothetical separate app couldn't: the API enforces it, not the client bundle. Combining the apps does not add an attack surface the separate-apps approach avoids.
- **Deployment complexity is lower.** One codebase, one release train, one App Store Connect/Play Console listing per platform to keep in sync with backend changes — directly relevant given this is a small team shipping fast, and matches the monorepo's existing single-`apps/mobile`-target structure (now becoming `apps/ios` and `apps/android`).
- **Future scalability**: if a genuine reason emerges later to split (e.g., materially different app-size/permission profiles, or a decision to sell the tenant app as a white-label product independent of the landlord product), that's a straightforward extraction from a well-modularized single app — going the other direction (merging two shipped apps later) is much more expensive.

**Where the master-prompt's role split still applies**: within each app, `PortalMode` (Landlord/Owner vs Tenant) drives navigation exactly as specified in §10.1/§10.2 — the tenant surface stays intentionally simple (Home, Lease, Payments, Documents, Maintenance, Meter Readings when enabled, Announcements, Notifications, Notices, Profile) and never renders other tenants, unrelated properties, owner financials, staff data, portfolio data, or accounting data, enforced server-side per role/org-membership.

## 6. Scope carried into native apps vs. web-only (per master prompt §10.1, cross-checked against the screenshot audit's desktop-to-mobile mapping)

**In the native apps** (owner/landlord + tenant, evidenced as reachable on PropView's own mobile-web surface and consistent with §10.1's "oversight, approvals, visibility, critical actions, portfolio monitoring" framing): Dashboard/KPIs, Properties (view/light edit), Units (view), Tenants (view), Leases (view + key actions), Rent status, Payments (log/view, approve EFT claims), Owner Statements (view, not draft), Documents (view/upload), Maintenance (full flow both directions — this is the master prompt's explicit native-app priority), Approvals (maintenance, applications), Announcements, Notifications, Tasks, Settings.

**Web-only** (per master prompt §10.1's explicit instruction not to reproduce complex desktop accounting on a phone, and consistent with the screenshot audit's finding that Trial Balance/Tax Pack/Organisation-compliance/Team-Seats/bulk-import/Portfolio-Map-authoring only ever appeared inside the wide-sidebar Landlord Console): Trial Balance, Tax Pack, Organisation compliance settings, Team Seats/RBAC management, bulk property/lease import, Applications & Screening review (multi-field comparison), Listings Studio/Articles/Sales & Auctions (if built at all — see open scope question in the matrix), Portfolio Map authoring, Audit History deep review.

## 7. Native capabilities to use from day one (master prompt §8/§9)

- **iOS**: Face ID/Touch ID via `LocalAuthentication`, Keychain for token storage, `PHPickerViewController`/`AVFoundation` for camera/document capture, `UNUserNotificationCenter` for push, Universal Links for deep linking, `URLSession` background upload tasks for document/photo uploads.
- **Android**: `BiometricPrompt`, Android Keystore-backed encrypted storage (`EncryptedSharedPreferences`/`DataStore`), CameraX for capture, Firebase Cloud Messaging or equivalent for push, App Links for deep linking, `WorkManager` for background uploads.

Both platforms replace the existing Expo app's `expo-secure-store`/`expo-local-authentication`/`expo-notifications` usage with these native equivalents — conceptually the same capabilities, implemented natively rather than through a JS bridge.

## 8. Reusable business logic vs. UI (from the existing Expo app)

Per the instruction to separate what's reusable "independently of its UI": almost nothing in `apps/mobile` is logic separable from its UI in a form portable to Swift/Kotlin, because it's TypeScript running in a JS runtime — it cannot be linked into a native binary. Treat `apps/mobile` as living documentation to consult while building native screens, then retire it once native parity is reached (`ARCHITECTURE.md`'s applications table already marks it "reference only during migration").

## 9. Offline support & synchronization (added by Production Readiness Review, 2026-07-30 — previously unaddressed anywhere in this document)

Not designed prior to this review. A property-management native app has real offline scenarios (a landlord walking a property with no signal, a tenant in a basement unit submitting a maintenance request) that a pure online-only client handles badly (silent failure or a blocking spinner with no recovery). Decision, scoped deliberately narrow for V1 rather than a full offline-first rearchitecture:

- **V1 scope: read-through cache + write queue for a short, explicit list of flows — not general offline-first.** A full offline-first architecture (local database, bidirectional sync engine, conflict resolution across every entity) is a major undertaking that this review does not consider justified for V1 given the master prompt's own native-app scope is already deliberately narrow (`MOBILE_ARCHITECTURE_DECISION.md` §6 — Maintenance full-flow first, most accounting/admin screens are web-only). Building a general sync engine for screens that are mostly read-only summaries (Dashboard, Properties view, Leases view) would be speculative complexity ahead of a real need.
- **Read paths**: the last successfully-fetched response for each screen is cached locally (iOS: on-disk cache keyed by request, e.g. `URLCache` or a lightweight local store; Android: `DataStore`/Room-backed cache) and shown with a visible "showing cached data from [time]" indicator when the network call fails — never silently stale data presented as live. This covers Dashboard/Properties/Leases/Documents view screens cheaply.
- **Write paths — only Maintenance ticket submission gets a real offline queue in V1**, since it's the explicit native-app priority flow (`MOBILE_ARCHITECTURE_DECISION.md` §6) and the one write action most likely to happen in a low-signal location (inside a property). A submitted-while-offline ticket is queued locally (with its photos) and retried automatically on reconnect (iOS: `BGTaskScheduler`/background `URLSession` upload task per §7's already-specified background-upload capability; Android: `WorkManager`, also already specified in §7) — the queue is visible to the user ("1 request pending upload") so it's never a silent, invisible retry. No conflict resolution is needed for this specific flow because ticket creation has no server-side state to conflict with (it's a pure insert, not an edit of existing data).
- **All other write actions (payments, approvals, settings changes) require connectivity in V1** — the UI disables the action and states why, rather than queuing something with real conflict-resolution stakes (e.g. two people editing the same lease offline) that this review does not consider safe to solve implicitly. This is a deliberate, documented V1 boundary, not an oversight: general write-conflict resolution across a multi-tenant, multi-staff system is exactly the kind of thing that's expensive to retrofit _badly_ but cheap to add _deliberately_ later, once real usage data shows which specific flows actually need it.
- **Sync strategy for V2+, if broader offline support proves necessary**: evaluate a proper local-first store (e.g. a local SQLite/Realm-backed cache with a defined last-write-wins or field-level merge policy per entity) once there's evidence (support tickets, usage analytics) of which flows actually need it — do not build this speculatively.

## 10. What this decision does NOT cover yet

This document records the _architecture_ decision (native, per-platform, role-aware single app) and scope split (native vs. web-only), evidenced from the audits.

Still not covered anywhere: a build/release pipeline design (Fastlane, TestFlight/Play internal testing) and the shared design-token JSON-export build step both native specs' §15/§14 flag as a real, small, not-yet-written implementation task. Both are genuinely blocked on having actual native projects to configure a pipeline or build step for — they follow once a real Xcode/Android Studio environment starts implementation, not before.
